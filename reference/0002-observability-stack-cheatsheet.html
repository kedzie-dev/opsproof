OpsProof 관측 스택 치트시트

판정은 Synthetic Check가 하고, 관측 스택은 실패 원인을 연결해 찾는다.

신호별 책임

신호수집·저장답하는 질문보관
MetricPrometheus언제부터 얼마나 많이 실패·느려졌나?7일
LogAlloy → LokiPod와 Kubernetes가 무슨 메시지를 남겼나?7일
TraceOTLP → Alloy → Tempo한 요청이 FastAPI·PostgreSQL을 어떻게 지났나?3일

Grafana는 세 저장소를 조회한다. Alloy는 전달자이며 저장소가 아니다.

실제 데이터 경로

Pod stdout/stderr ─┐ Kubernetes events ─┼→ Alloy → Loki ───────┐ OTLP trace ───────┘ ↓ │ Tempo ─────────┼→ Grafana (조회) ↓ remote-write│ Kubernetes metrics ─────→ Prometheus ──────┘ ↑ Tempo: span metric / service graph

이 Lab에서 기억할 세 가지

  1. opsproof-order-api는 OTLP gRPC endpoint k8s-monitoring-app.…:4317로 trace만 보낸다. OTEL_METRICS_EXPORTER=none, OTEL_LOGS_EXPORTER=none이다.
  2. 앱 JSON stdout은 코드 변경 없이 Alloy가 Loki로 보낸다. observability namespace 자체는 수집에서 제외한다.
  3. Tempo는 trace를 3일 저장하고, metric generator가 span metric·service graph를 Prometheus로 remote-write한다. 그래서 Prometheus에서 traces_spanmetrics_calls_total을 조회할 수 있다.

원인 탐색 순서

1. Synthetic Check 결과: 계약 통과/실패를 확정
2. Loki: 같은 시각의 API error와 Kubernetes event 확인
3. Tempo: 실패 요청의 FastAPI → psycopg/PostgreSQL span 확인
4. Prometheus: 실패율·지연이 언제, 얼마나 변했는지 확인

경계: Grafana의 빈 화면은 “계약이 통과했다”는 증거가 아니다. 이 로컬 stack은 single replica, short retention, PVC 5Gi이며 production 관측 플랫폼이 아니다.
